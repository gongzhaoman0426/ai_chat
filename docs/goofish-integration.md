# 闲鱼接入与客服工具

更新日期：2026-09-10。

## 实现范围与验证等级

平台标识为 `goofish`，统一显示为“闲鱼”。新手引导、连接店铺弹窗、店铺设置、工作台和 Agent 调试均可选择闲鱼。使用独立 Electron 持久化登录分区，窗口隐藏后继续监听，退出软件后不再运行。

已接入的代码能力：

| 能力 | 实现方式 | 边界 |
| --- | --- | --- |
| 登录与账号归属 | 网页 `loginuser.get`、SDK 身份核对 | Store 使用 `mainUserId`，缺失时使用 `userId`；Account 使用实际 `userId`。平台不同或主账号不同不会共享店铺身份 |
| 实时文本与图片接收 | SDK 消息监听及底层消息事件 | 仅接待能够核实当前账号是商品卖家的单聊；其他私信不猜成买家咨询 |
| 人工、AI 文本发送 | 当前会话 `sendMessage` | 先显示发送中；仅匹配服务器回执才确认为已发送 |
| 图片发送 | 闲鱼网页使用的图片上传接口，再发送图片内容 | 上传成功不是发送成功；上传前后检查身份和会话；支持 PNG/JPEG/WebP/GIF |
| 平台人工回复同步 | 识别当前账号/主账号发出的成功消息 | JuDesk 自己的发送回执关联已有 Outbound，不再次作为人工回答学习 |
| 已读 | 查看会话后由宿主异步调用 SDK | 不提供给 Agent，不等同于接管会话；仅标记当前会话已保存的买家消息 |
| 历史查询 | 底层 SDK `listPrevMsgs(sessionId,cursor,limit)` | 不切换网页选中会话，不把查询结果作为新消息触发回复 |
| 买家资料、咨询商品、商品列表及详情 | 固定 MTOP 接口与限定输出 | 商品详情还须核对卖家；未知数据结构报错，不返回虚假的空列表 |
| 关联订单、订单详情、物流/交付记录 | 当前会话交易信息与订单接口 | 订单列表是平台在当前会话中关联的订单，`partial=true`，不声称覆盖买家的所有历史订单 |
| 无需物流发货 | 准备、宿主授权、单次提交、结果读回 | 仅在该订单返回明确的 `consign.dummy` 操作时可执行；普通快递发货没有已验证契约，不映射到此接口 |

“代码已接入”不等于实际账号验收通过：自动化测试使用隔离夹具模拟消息、上传与订单，不向真实买家发消息，也不修改真实订单。真实网页只读检查确认目前能提取 SDK、回执客户端和 MTOP。真实账号登录、平台最终送达、图片权限、订单响应与发货读回仍须按本文验收。

## 依据

最初参考文件是 `docs/references/xy_inject.js` 和 `xy_demo.js`，不是可直接加载的生产桥接。实现统一使用 `window.__judeskBridge`，不要求调用者预先定义 `imsdk`、`_imsdk` 或 `lib` 局部变量。

2026-09-09 补充读取了闲鱼官网当时公开加载的 `xy-site/0.0.174` 脚本，只用于核对调用契约，没有把第三方整包代码复制到项目：

```text
https://www.goofish.com/im
https://g.alicdn.com/idle-pc/xy-site/0.0.174/js/p_im-index.js
https://g.alicdn.com/idle-pc/xy-site/0.0.174/js/p_layout.js
https://g.alicdn.com/idle-pc/xy-site/0.0.174/js/p_item-index.js
https://g.alicdn.com/idle-pc/xy-site/0.0.174/js/p_order-detail-index.js
```

官网脚本揭示的关键区别：

- `registerMessageChangeLisnter` 实际存在这个拼写，返回 Promise 包装的取消订阅函数。
- `onAdd` 包含本地发送中的消息，不能全部作为“平台已发出的人工回答”。
- `sendMessage()` 的 Promise 成功值为空；服务器发送结果通过 `paas.message.changed` 的 `recordStatus`、`messageModel.messageId` 与扩展字段传递。
- `sendState` 的成功/发送中/失败值分别为 0/1/2；连接状态 4 表示认证完成。降级或仅自身可见状态不能当作送达。
- SDK 会把业务 `extJson` 放进消息扩展。因此用每个 Outbound 的 ID 关联回执，不按文字相同或最近发送时间猜匹配。
- `pc.user.query` v4 的 `data.userInfo` 可以不包含 `userId`，官网 SDK 使用请求范围中的身份补齐；实现也先核实会话，再绑定返回资料，若平台显式返回其他 ID 则拒绝。
- 图片采用业务 `contentType: 2` 和 `image.pics`；网页上传使用 `appkey=xy_chat` 的 `stream-upload.goofish.com` 接口。
- 2026-09-10 登录账号只读查询：商品头部 `left.data.picUrl`、店铺商品 `absoluteMajorPicture`、商品详情 `itemDO.imageInfos[].url` 实际返回 HTTP 的 `img.alicdn.com` 地址。桥接仅对允许域名将 HTTP/相对协议转换为 HTTPS，图片路径与查询参数保持不变；应用内验证 3 张商品图均可正常加载。商品详情保留原有主图与详情图片作为候选，详情弹窗优先展示详情图片；未知域名、凭据 URL 和其他协议不接受。
- 消息历史使用按会话读取的底层接口。高层 `listPreviousMessage` 会操作当前 UI 消息列表，不用于聚合工作台的多会话查询。

Webpack 发现按模块功能签名和实际方法校验，不依赖固定数字模块 ID、固定 `.h` 导出名或固定 chunk 名。重复注入不重复注册，升级和 SDK 更换会清理旧监听。页面原有 SDK 负责登录会话和网络协议；JuDesk 不保存额外平台密码，也不自建一份消息长连接。

## 消息处理与接待

```text
闲鱼消息事件
  → 核实当前登录身份、会话参与人、商品卖家
  → 稳定 ID 去重，识别方向/历史/撤回/消息类型
  → WorkbenchHost → Engine
  → 原有接待状态、问答规则、Agent 执行
  → Outbound → 闲鱼 SDK → 服务器回执
  → 实际回答进入原有学习流程 → 人工审批
```

平台发现不调用模型，平台选择不调用模型，没有增加一次分类或格式化模型请求。AI 回复、人工异步发送、显式接管、学习候选审批继续使用同一套核心流程。

发送状态遵循现有 `confirmed / rejected / unknown` 契约。回执必须与 Outbound ID、当前会话、当前发送身份匹配；函数返回空值、上传成功、本地待发送事件都不能确认送达。晚到的准确回执可以修正 unknown；unknown 不自动重发。

历史消息只作为上下文。消息事件使用稳定平台 ID，不用随机 ID 填补缺失字段。长 ID 保留字符串；已经发生数字精度损失的消息或业务资料拒绝使用。

当前实现不把无法确认商品卖家的私信自动交给 AI。无商品关联会话、群聊及其他特殊会话需要取得明确的接待角色契约后扩展。

## 统一 Toolkit 与范围

继续使用一个“店铺客服工具”，新版本为 `builtin/commerce@1.1.0`。

| Toolkit 成员 | 闲鱼实现 |
| --- | --- |
| `buyer-profile` | 当前买家资料 |
| `conversation-item` | 当前咨询商品头部信息 |
| `goods` | 当前卖家的商品列表（网页“我的宝贝”范围） |
| `goods-detail` | 当前卖家商品详情 |
| `buyer-footprint` | 闲鱼没有完整浏览足迹；合并会话交易卡片与当前咨询商品，并标明 partial |
| `history` | 按会话、游标读取历史 |
| `buyer-orders` | 当前会话关联订单，返回本轮 `orderRef` |
| `order-detail` | 使用本轮 `orderRef` 查询详情 |
| `order-logistics` | 使用本轮 `orderRef` 查询物流或无需物流交付记录 |
| `ship-order` | 平台明确支持时执行无需物流发货 |

闲鱼不挂载 PDD 的订单备注和 SKU 查询，也不开放任意 `mtop(api,data)` 或任意 SDK 方法调用。

Agent 输入中不能选择平台账号、店铺、买家或任意会话。宿主从执行上下文读取 Account → Store → Conversation；`PlatformHosts` 按账号选择驱动。会话上下文通过通用链路传递，取消此前仅抖店传递会话上下文的特殊分支。

四类资源的“可用店铺”继续生效。工具需要同时满足资源范围、当前平台 operation 和当前账号 capability。问答检索/话术只包含通用问答与本店问答，学习候选归属当前 Store。

## 发货与订单写操作

`ship-order` 接受当前运行产生的 `orderRef`、`deliveryMode: no_logistics` 和交付说明，不接受模型填写任意订单号。仅可用于已经真实交付、且商家授权的业务场景；买家催发货本身不构成完成交付的证据。

执行链路：

1. 在本轮当前账号、店铺、买家和会话范围内解析未过期订单证据。
2. 闲鱼桥接重新读取关联关系和订单详情，确认仍存在明确的无需物流发货操作。
3. 宿主将订单、买家、卖家与交付说明发回业务进程核验；这一步是执行资格检查，不增加模型请求。
4. 数据库动作从 prepared 变为 dispatched 后，才提交固定接口。
5. 读取无需物流交付记录与最新订单，结果一致才返回 confirmed。
6. 中断或读回不符返回 unknown。相同店铺同一订单跨运行、重新启动或更换文案都不重复提交。

发货走独立 `executeShipment` 契约，订单备注仍走 `executeAction`，不会把“追加备注”误映射成发货。没有接入退款、取消交易、改价等本次参考文件之外的写操作。

## 账号验收

在自己的测试会话完成，使用相同设备上的应用窗口与隐藏状态分别验证：

- 登录主账号/子账号，核对店铺归属；退出登录、切换账号、重开软件不会串店。
- 买家发送文本与图片，包括未选中的会话；工作台只出现一次，购买方向的私信不会误回复。
- 人工发送文本、图片，发送中 → 平台确认；断网或平台拒绝不显示已发送。
- 在原平台人工回复，工作台同步且参与原有学习；学习结果仍需人工审批。
- 同一 Agent 接待 PDD/抖店/闲鱼，工具成员随真实店铺变化，不能借参数切换其他账号。
- 商品、买家、订单和物流响应符合当前返回结构；结构不符时保留错误信息补充适配，不伪造空数据。
- 只对专用测试订单验收无需物流发货，核对真实交付记录与重复提交防护；普通快递发货不可使用此工具。

平台网页和非公开 SDK 会变动，真实账号验收结果应补录到实现与验证记录。

## 会话订单侧栏显示为空（2026-09-23）

在已登录的闲鱼 `xy-site/0.0.175` 页面通过开发者控制台只读核对：同一买家会话在原平台显示已发货，但 `mtop.idle.trade.message.chat.tradeinfo` 成功返回 `module.items: []`，同时提供新版嵌入页面 `kunEmbedUrl`。现有实现只从这个列表提取订单号，所以误显示“当前查询范围内暂无订单”。

同一会话的 `mtop.idle.trade.pc.message.headinfo` 返回 `commonData.orderId`、`itemId`、`seller: "true"` 及订单状态；用这个订单号读取 `mtop.idle.web.trade.order.detail` 能取得匹配的 `orderId`、`peerUserId` 和 `seller`。详情标题与状态位于 `components` 中的 `orderInfoVO.data.itemInfo.title` 和 `orderStatusVO.data.orderStatusInfo.title`，成交金额位于 `orderInfoVO.data.priceInfo.amount.value`。

修复合并当前会话的交易列表与头部卡片中的明确订单号，去重后查询详情；仍保留当前账号、买家、会话、商品与订单归属检查。一处来源请求失败但另一处有明确订单证据时保留可用订单并提示部分查询失败；缺少订单证据且接口失败时保留错误，不伪装成正常空列表。明确的归属冲突直接拒绝，详情中的顶层与嵌套归属字段均需一致。列表查询复用本轮关联证据，单独查询详情及发货准备继续重新核验。返回范围仍是当前会话关联订单，不代表买家的所有历史订单。

验证：闲鱼桥接、工具运行时、工作台和查询契约共 4 个测试文件、83 项测试通过，TypeScript 与改动代码的格式检查通过。备份并更新本机已安装应用的闲鱼桥接资源、正常重启后，原空列表会话显示商品标题、成交金额和“已发货，待买家确认收货”；详情弹窗正常显示，另一无订单会话仍为空。此次真实平台验证仅查询资料，未发送客户消息或提交订单操作。源码及本机资源已更新，发布安装包尚未重打。

## 登录完成后没有自动添加店铺（2026-09-09 修复）

现场检查确认：闲鱼网页已显示登录账号，`loginuser.get` 返回有效的数字字符串 `userId`，但登录后的文档没有 JuDesk 桥接对象，数据库也没有闲鱼账号。该账号的返回只有 `userId` 与解密字段提示，不含 `mainUserId` 或昵称；个人卖家按 `userId` 建立店铺身份，不依赖已有聊天或商品记录。

宿主原先在 `loadURL` 完成后才启动轮询，轮询又用一个跨导航的 `busy` 标志等待页面异步调用。旧登录文档的加载或身份请求没有返回时，新页面会一直无法注入。修复后：

- 打开窗口后独立启动检查，页面的 DOM 就绪即可解除导航等待。
- 主文档导航、页面进程退出和账号恢复会取消旧检查；旧任务的收尾不会覆盖新任务状态。
- 页面检查最长等待 15 秒，超时后可自动重试。后台 MTOP 使用官网的 `AutoLoginOnly` 请求方式及 10 秒网络超时，不另外启动登录弹窗。
- 首次添加阶段也在平台窗口标题显示状态，错误同步提示到工作台；平台拒绝对象转换为登录/接口原因，不显示 `[object Object]`。
- 重复点击添加会复用尚未识别的同平台登录窗口，避免另开一个无登录态的分区。

回归包括单元测试中的永不结束的加载/身份请求、登录导航取消、超时恢复、个人卖家返回结构与首次错误提示，以及真实 Electron 内两个文档切换后的自动注册、收发和回执。平台网络仍使用隔离夹具。真实账号的最终送达能力需要另行验收。

现场验证补充：重启修复后的构建并由用户重新完成闲鱼登录后，实际账号通过正常注册链路自动写入 Store/Account；数据库连接阶段为 `online`，工作台店铺选择器显示闲鱼账号，页头显示“闲鱼已连接”。没有手工插入账号记录，没有代发真实客户消息或执行订单写入。真实登录与消息通道识别已验证，买家端最终送达仍不包含在此次验证中。
