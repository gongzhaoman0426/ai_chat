# 接待中心与业务操作

> 2026-09-11：本轮新增能力及验证边界见 [客服工具扩展](commerce-capabilities.md)。下文早期能力清单以该文档和当前平台能力表为准。

更新日期：2026-09-28。

## 统一接待界面

接待中心统一展示聊天记录、回复入口和业务侧栏，无需切换接待模式。AI 是否自动回复由店铺开关和会话接管状态决定；查看界面不改变店铺自动回复、学习开关或人工接管状态。旧的本机接待模式偏好不再使用。

- 店铺筛选位于会话列表上方的下拉框，可选择全部店铺或某一家店；会话列表与聊天占据主体，不显示顶部店铺概况卡片。选中会话直接展示回复输入框和接管/交还入口。
- 「客户 / 商品 / 订单 / 记录」侧栏绑定当前会话的实际接待账号；宽窗口并排展示，较窄窗口通过「客户与订单」打开抽屉。
- 店铺筛选与当前会话独立：打开客户不改变范围；「待处理」和「我接待的」分开。清除未读或接管后，当前聊天不因筛选结果变化而消失。会话支持游标分页。
- 文本与已选图片草稿按店铺和会话独立保留，切换页面、会话后仍可继续编辑；草稿仅在当前进程内保存，重启后不保留。人工文本发送延续原有后台队列。
- 查看聊天、查询资料、发送人工文字/图片/富消息和确认普通订单业务操作均不接管。只有点击「接管会话」或明确确认「转接客服」才转为人工接待；处理完成需要主动「交还 AI」。离开会话不会自动解除接管，AI 主动转人工的等待规则继续保留。

### 拼多多客服转接

接待中心选择会话后，从「客户与订单 → 转接客服」打开。2026-09-10 已登录页面核验：当前 SDK 导出绑定后的 `moveConversation(params, callback)`，没有旧 `moveconv`；原先只检测旧名称导致账号上报 `staffTransfer=false`，按钮被隐藏。桥接现优先使用新版方法，同时保留旧版兼容。

`getAssignCsList` 当前返回 `result.csList` 对象。对象的键是原平台传给转接命令的客服路由 ID，条目的 `id` 是商家账号 ID，两者可能不同；原平台也是使用对象键构造 `customerId`。解析时以键作为目标，按条目账号 ID 排除当前登录客服，展示非空昵称或账号名称；仍兼容旧数组格式。实测当前账号仅返回自己，因此入口可见，弹窗应显示「暂无其他可转接客服」，其他客服上线并具备权限后可刷新。

新版 SDK 返回 `void`，转接结果等待本次调用的回调，最长 12 秒。明确成功才确认，明确拒绝保留平台原因，缺少回执则记录待核对；超时不重试旧接口或重复提交。提交仍经过会话绑定、客服列表复查、显式确认及去重；只读验证不实际转移客户。

本次验证：`pnpm build`、PDD 桥接/宿主及接待业务共 62 项回归测试、`scripts/workbench-smoke.mjs` 通过。已在当前账号只读检查新版方法与客服列表，确认自身账号排除后无其他目标；接待中心的拼多多会话已显示转接入口。成功/拒绝/超时及去重只在隔离夹具中执行，未实际转移客户。

### 抖店可转接客服列表

转接弹窗读取 `getCanAssignStaffList` 的当前候选人，排除本会话实际接待账号；飞鸽的 `PCUIModel.state.serviceList`、`onlineservice` 和 `getOnlineCustomerInfo` 不能代替可转接资格。2026-09-10 只读核验发现，同一店铺的通讯录返回 5 个客服，可转接接口曾返回空数组，之后仅返回当前登录客服；`/backstage` 与 `/pcbackstage` 结果一致，按另一客服的 `staff_id_str` 查询仍为空。未加入分流分组是原平台同时显示的提示，尚不能认定它就是其他客服不可转接的原因。

原始响应为 `{ code: 0, st: 0, data: [{ staffId, staffName, ... }] }`。按飞鸽实现优先使用 `staffIdStr`，兼容字符串 `staffId`；缺少精确 ID 时拒绝使用已丢精度的数字。空数组及只有本人都显示「暂无其他可转接客服」，提示核对在线、权限和分组配置，并提供「打开原平台」「刷新客服列表」。接口拒绝、验证要求和未知结构继续显示查询错误。每次重新打开弹窗重新查询；刷新时禁用确认，旧客服引用失效后须重新选择，实际提交前仍重新检查目标资格。

### 订单空结果与商品图片

2026-09-10 当前账号只读核验：拼多多 `userAllOrder` 对无订单买家返回 `success: true`、`result.total: 0`、`result.orders: null`，分页字段也可能为 `null`。这不是接口失败。适配器只对明确的 `orders: null + total: 0` 转为空数组、保留请求分页并标记无下一页，订单页显示「当前查询范围内暂无订单」。列表字段缺失、类型未知或 `orders: null + total > 0` 仍报查询错误，平台拒绝及买家归属检查保持生效。

同次闲鱼查询确认：当前咨询的 `left.data.picUrl`、店铺商品的 `absoluteMajorPicture`、详情的 `itemDO.imageInfos[].url` 均可能返回 `http://img.alicdn.com/...`。桥接对允许的闲鱼/CDN 域名转换为 HTTPS，保留路径及查询参数；非平台域名、凭据 URL 和非 HTTP(S) 协议继续过滤。主图无效时尝试已知备用图片字段。

商品图片使用无 Referer 的 HTTPS 请求；加载失败显示占位图，图片地址更新后重新加载。详情弹窗优先使用详情响应中的图片，缺失时使用列表缩略图。查询错误、平台无结果与部分成功分别呈现，并显示查询时间。库存、价格只是查询时信息。

本次验证：构建、121 项相关回归测试及 Electron 工作台测试通过，包含缩略图失败后加载详情图片、刷新后恢复新缩略图。真实 IPC 查询验证拼多多当前客户 0 笔订单；闲鱼当前咨询、3 件店铺商品、关联商品和详情均包含图片，3 张不同图片在应用渲染进程中成功加载。只读查询未发送客户消息、执行订单操作或调用模型。

## 共用业务服务与独立人工上下文

```text
人工右侧栏 ── workbench.* IPC ── WorkbenchService ─┐
                                                ├─ CommerceService ─ PlatformHost ─ 各平台适配器
回复 Agent ── 店铺客服 Toolkit ─ ReplyPlatformTools ┘
```

`ReplyPlatformTools` 兼容导出现在指向共享 `CommerceService`。查询、订单证据、拼多多备注和闲鱼发货复用同一实现；人工操作不创建 AiRun、不依赖模型/Agent 配置、不需要开发者模式，也不增加模型请求。原生转接由 WorkbenchService 单独调度。

`WorkbenchSession` 固定 `storeId / accountId / conversationId / buyerId / routeVersion`，30 分钟有效。上下文接近到期时刷新为新会话；过期订单或客服引用需要重新查询。后端每次查询、返回资料及写入授权时重新检查账号存在、店铺归属、路由、在线状态与当前能力；界面切换只改变展示，不改变已确认操作的目标。

`PlatformEvidence`、`PlatformAction` 可归属 AI 的 `runId` 或人工的 `sessionId`。人工查询使用独立证据空间，订单引用只允许在同一会话、店铺、账号、买家范围内使用，有效期 5 分钟。不能把另一个会话或 AI 执行中的 `orderRef` 搬过来操作。

前端查询缓存按 session、操作和参数隔离。聊天和普通本地数据刷新不会自动重新查询平台；主动刷新、切换查询页等才读取平台。后台每分钟刷新本地业务上下文，检查连接和会话有效期。

## 操作确认、回执与恢复

1. 商品与订单查询直接执行。备注、发货、原生转接先展示具体店铺、客户、目标和说明，由用户确认。
2. 提交带有独立 requestId。同号同内容复用结果，同号异内容拒绝；同会话人工写操作串行执行。
3. 下发前复核实际账号及目标，持久化 `prepared → dispatched → confirmed / rejected / unknown`。只有明确的回执或读回核实才显示成功。原平台 SDK 返回空值不代表转接成功。
4. 闲鱼发货按店铺和订单全局去重，与 AI 工具共用记录。已有尝试不会因为换了 Agent、文案、人工会话或重启而重复提交。拼多多备注保留原标签与备注，并比较和读回；平台缺少 CAS 令牌，不能宣称与其他客服的修改原子互斥。
5. 未完成操作、未知回执及尚未人工核对的成功转接会阻止交还 AI。用户在「记录 → 已在原平台核对」填写核对结果后，才可以主动交还。转接还须先确认当前账号在原平台具有接待资格。
6. 人工核对保留原回执状态，另存 `reviewedAt / reviewNote`，不把未知状态改为成功，也不重发平台操作。
7. 应用重启：未下发操作标为未提交，已下发无回执操作标为待核对；不自动重放业务写入。人工接待状态仍然保留。

「记录」显示当前会话最近 100 笔人工和 AI 业务操作。CSV 导出当前会话全部记录，含时间、来源、目标、结果和人工核对说明；采用 UTF-8 BOM、CSV 转义与公式前缀保护。模型逐步调用仍在「Agent 执行」查看，两者不是同一种记录。

## 后续接口如何接入

提供接口时需要同时给出参数、身份和订单归属、成功/失败/未知回执，以及可查询最终状态的方法。随后按以下层次扩展：

1. 在 contracts 中增加查询或操作 schema、平台能力和业务名称。
2. 平台适配器解析真实返回，桥接只在检测到对应能力时上报，使用当前账号登录会话。
3. 共享业务服务增加范围检查、目标证据、幂等策略、提交授权与结果核实；涉及金额时使用明确币种和整数最小货币单位，并核验当前订单状态与额度。
4. 工作台增加对应卡片和确认表单；是否向 Agent 开放单独评估，不能因人工入口已实现就自动挂载给 AI。
5. 接入处理记录和导出，补充隔离测试，再用测试账号验证真实平台。

退款和小额补偿现在没有可调用的占位接口或虚假成功按钮。后续完整接口可接入现有会话、授权和记录流程，无需另建一套工作台。
