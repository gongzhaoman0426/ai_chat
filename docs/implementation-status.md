## 与参考项目的关系

`agent-platform` 提供了 Agent 草稿 / 发布、集合工厂、设置字段和原生 Workflow 的参考；JuDesk 使用自己的本地绑定、发布快照、SDK 与业务控制，不引入组织和团队壳。

`botsdk/PddWorkbench/Windows/MainWindow.axaml.cs` 提供 PDD 账号识别、SDK 发现、发送和回显的线索。JuDesk 实现了独立 Electron 账号分区、固定桥接协议、持久化 ACK 和 OutboundMessage 确认，不运行 botsdk 的本地 WebSocket 服务。

两个参考项目均未作为运行时依赖；分发 JuDesk 不需要它们。设计文档的 A01–A73 保留为后续平台联调和发布验收清单。

## 自动回复阻塞及发送回执修复

真实账号排查发现三处独立问题：

1. 账号通道在线、自动回复开关已开，但账号未记录验收。早期回复任务在模型调用前失败，界面仍误显示“AI 接待中”。
2. 当前拼多多 SDK 的 `sendMsg` 先返回，再延迟约 50ms 提交请求。旧桥接过早清除命令关联，导致已出现在平台上的人工发送在本地仍为 unknown。
3. 用户完成验收后，GLM 实际调用成功，但最终返回普通文字，没有产生 ReplyCandidate。单独注入 JSON schema、启用 json_object，以及强制工具提交在后续真实测试中仍收到普通正文。因此最终采用原生正文路径，不再把正常客服正文当成格式错误。

### 最终实现

- 开关、消息入队和最终发送统一核对账号就绪条件。未连接或未验收时不能开启自动回复；历史已开启的开关仍可关闭，但显示暂停原因和设置入口。多账号逐个判断，不共享验收资格。
- 用户验收通过后立即更新验收时间、能力快照及审计记录，不补发旧消息。排队后失去资格的任务只失败一次，不反复重试。
- 桥接 v14 保留命令关联直到精确请求回执或超时；图片上传前即占用本账号发送位置。回执必须有对应请求 ID 和平台消息 ID，不能根据相似文本或时间猜测，已有待确认记录不自动改写。
- 普通回复采用 Agent 正常完成的最后一步正文，由本地代码构造 ReplyCandidate，再由业务服务检查和发送。只取最终文字，不发送推理或中间工具说明，也不接受空正文、截断输出或失败结果。正文的 evidenceIds 来自真实上下文依赖，不冒充模型给出的引用。
- 图片或显式动作仍可通过同一轮 `submitReply` 工具参数提交；工具只保存候选，提交后立即结束。转人工继续使用控制工具。工具参数无效时不会回退到正文。所有路径均没有额外的模型格式整理 / 修复步骤。
- 普通问候等直接回复只需一次模型请求。确需先查知识 / 调用其他工具时保留原有 Agent 循环，达到配置的最大步骤后停止。无效提交、工具失败、空正文或截断输出均停止，不为修复格式额外请求。
- 回复的 schema、证据、附件、账号和会话资格检查保留。生成期间人工打开会话只取消旧输出，不会因终止工具校验失败而误设置新的转人工状态。
- 学习仍独立运行、单次生成结构化评估，GLM 使用 json_object 与 schema 提示；候选一律需人工审批。没有更改用户的模型、token 上限、知识库或 Agent 发布版本。新回复协议使用独立的派生记忆线程，避免历史未发送的失败草稿继续干扰模型；实际聊天记录仍由业务库提供，未删除。

### 验证范围

本地 HTTP 夹具使用真实 Mastra，断言工具提交 / 先检索后提交 / 无效提交 / 普通正文分别请求 1 / 2 / 1 / 1 次，正文与工具提交均覆盖成功路径，并验证转人工立即停止、循环步数上限、正文的生产入库到发送队列、推理与中间说明不外发、空 / 截断正文拒绝、伪造证据拒绝及人工接管竞态。所有主动自动化测试均使用临时资料库、本地模型及模拟发送宿主。

真实账号的新测试消息已在最终版本完成一轮自动接待：`AiRun.status=succeeded`、`usage.outputMode=agent_text`、`output.action=reply`，关联 `OutboundMessage` 的 `origin=ai`、`status=confirmed`。这验证了当前账号的真实模型生成到拼多多精确回执链路，未使用额外格式整理模型。该模型调用由用户自己的测试消息触发，助手未主动向客户发送测试消息、未代替用户确认验收。

这是一轮文字自动回复的实测，不扩展为图片、全部工具、多账号、长时间运行等场景均已验收。历史失败不会补发，由前次错误进入的等待人工状态也不会自动清除。

最终检查：7 个测试文件、62 项测试通过；类型检查、格式检查与构建通过；源码输出及 macOS arm64 `.app` 的 Electron 冒烟均通过，其中正文和工具提交分别验证只用一次模型请求。当前开发窗口已加载最终实现，账号登录和资料保留；更新后的桌面产物位于 `dist/mac-arm64/JuDesk.app`。

## 自动学习缺失结果与重复请求修复

用户提供的学习失败记录在生成完成后对 `undefined` 做 Zod 对象校验；旧代码仅使用 `response.object`，且校验失败前没有保存结束原因和用量，同一任务随后被按普通故障重试。历史记录不足以确定该次是否达到 token 上限，不能把 usage={} 当作没有调用模型。

- 学习改用单次完整 JSON 正文读取与本机严格校验，不添加第二个格式化 Agent、不补齐虚构评估、不接受截断或推理正文作为结果。评估器版本更新为 `learning-json-v2`。
- 仅对 GLM-5.3 / GLM-5.3-Flash 的学习调用设置 `reasoningEffort=low`，测试断言出站请求包含 `reasoning_effort=low`。保留模型的 maxTokens，不关闭该模型强制开启的 thinking，不改变回复路径或其他模型参数。
- 在输出 / 来源校验前持久化结束原因、token 用量和诊断元数据。空 / 截断 / 无效 JSON / 无效字段 / 虚假证据的失败立即停止自动重试，用户修正配置后可手动重试；暂时性请求故障仍有界重试。
- 有效结果仍只产生 pending_review 候选，学习没有审批、发布或发送能力；既有来源与配置版本检查保留。历史失败记录不改写，不主动回放真实问答。

## AI 生成成功与平台发送结果区分

一次“AI 已生成”只表示问答匹配或模型生成完成，不表示拼多多已接收。平台发送必须检查关联的 `OutboundMessage`：只有取得精确请求对应的成功回执与平台消息 ID，才能标为 `confirmed`，归档实际回答并进入学习来源。

本次排查的回复运行成功，关联发送却是 `unknown`、无平台消息 ID；旧桥接未保留平台拒绝或 SDK 异常的细节，无法从历史日志还原具体平台原因。该记录保持原状，不推定成功、不自动重发。

- 桥接 v15 同时处理精确的成功回执和明确拒绝。平台明确失败时即使包含 `msg_id` 也不确认发送，保存有限长度的错误码与错误说明，不保存完整平台载荷、Cookie 或凭据。
- 同时使用 `sendCmdMsg` 钩子与本次 `sendMsg` 的独立 `cb`，兼容延后请求、内部 SDK 实例差异及迟到回执；重复回调只形成一次确认或拒绝事件。SDK 原有的平台处理逻辑继续执行。
- 超时区分“未观察到请求提交”“请求已提交但回执未到”“回执缺少可确认信息”；传输异常仍为 `unknown`，不把它等同于未发送。明确拒绝为 `rejected`，不会用强制发送参数绕过平台限制。
- 迟到拒绝与迟到成功都先持久化，再 ACK 桥接事件；明确拒绝先于发送调用返回时幂等处理，不被随后返回的 unknown 覆盖。unknown 不盲目重发。
- “运行记录 → AI 运行”直接关联全部发送记录，分别展示生成 / 转人工结果与“发送成功、发送待确认、发送被拒绝、发送已取消”等状态。详情包含发送 ID、平台消息 ID、错误说明。无发送记录的已生成回复显示“未提交发送”，转人工提示显示其单独发送结果。
- 这些改动不增加模型请求；只有确认发送的业务回答进入学习，学习候选仍需人工审批。

验证使用隔离资料库、模拟平台回执和本地 HTTP 模型，覆盖平台拒绝、传输异常、请求 ID 不匹配、独立 callback、重复 / 迟到回执、持久化失败重试 ACK，以及 Electron 界面的生成与发送状态区分。未主动发送真实客户消息或回放历史回复。

验证结果：8 个测试文件、98 项测试通过；类型检查、格式检查、生产构建、源码版与 macOS 打包版 Electron 冒烟通过。当前开发实例已重新加载修复，原发送记录仍保留 unknown，未重发。


## 会话话术预览与一键发送

发送框工具栏的“话术”在当前会话内打开问答预览，不再跳转问答库。面板展示通用及当前店铺全部未删除问答的最新版本，包括文字回答、图片缩略图及适用条件；支持按问题、答案、适用条件搜索，以及全部 / 文字 / 图片筛选。停用和过期条目显示对应状态，人工可以按实际会话选择使用，不改变 AI 自动回复的知识资格；尚未审批的学习候选不进入话术列表。

- 点击卡片通过既有 `messages.send` 人工发送通道直接发送回答；文字按原文发送，图片发送已入库的原附件，不把图片说明或问题拼进消息。
