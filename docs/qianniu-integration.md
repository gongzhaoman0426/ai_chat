# 千牛 Windows 客户端接入

千牛接入采用预处理的 Windows x64 客户端。JuDesk 提供页面脚本、账号及消息桥接、登录后的自动 Hook 和接待工作台；客户端安装包由发布方准备并上传 Cloudflare。

## 客户端与下载配置

预处理客户端写入的固定脚本 URL：

```text
http://127.0.0.1:3000/qianniu-inject
```

JuDesk 启动后在 Windows 上提供该地址。客户端应在聊天页面加载脚本；脚本等候登录身份与 SDK 就绪，再连接本机桥接服务。应先启动 JuDesk，再启动千牛。客户端不能把脚本响应永久缓存，因为响应包含本次运行的连接令牌。该 URL 不需要跟随安装目录或安装版本变更。

下载地址在 `resources/qianniu.json` 中配置：

```json
{ "downloadUrl": "https://updates.quantaflow.one/qianniu.zip" }
```

地址必须为 **HTTPS**。若以 `.zip` 结尾，句达会在应用内**静默下载并解压**到本机数据目录 `qianniu-client/`，校验 `webui.zip` 中含固定脚本 URL 后缓存可执行路径；非 zip（安装器等）仍在系统浏览器中打开。空地址时禁用下载按钮，仍可点击“启动千牛”启动已安装的适配客户端。JuDesk 自动发现并缓存其路径，不需要用户选择 EXE；缓存保存在数据目录的 `qianniu-client.json`，不包含账号密码。

自动发现读取运行中的千牛路径、Windows App Paths/卸载注册项和常见 `QianNiu` 安装目录（含版本子目录），不会扫描整个硬盘。发布的安装包应登记安装位置。启动前会核对 `Resources/newWebui/webui.zip` 中 `recent.html` 的脚本 URL；未写入该地址的普通千牛不会被启动或注入。客户端自动更新覆盖适配资源后，需要重新安装适配版本。

## 用户流程与无感连接

1. Windows 用户在连接店铺或首次配置中选择千牛，下载并安装适配客户端。
2. 点击 JuDesk 的“启动千牛”。系统自动定位已安装的适配客户端并启动；未发现时提示安装后重试。
3. 用户在千牛登录并进入聊天工作台。JuDesk 识别登录后自动连接 Hook，没有手动注入步骤。
4. 页面消息连接与原生发送连接匹配到同一客服账号后，店铺进入在线状态。先验收收发，再开启自动接待。

多店铺登录：已有账号连接时，入口显示“登录其他店铺”。点击后再次调用适配千牛的启动器，打开额外登录窗口，现有账号继续运行。新账号登录并进入聊天工作台后，句达按各自完整登录名连接、按主账号昵称归属店铺。连接引导逐个显示账号状态；一家已连接时，其他账号仍可重试消息连接。添加账号不会清除已经手动断开或移除账号的记录；需要恢复旧账号时，使用其原有的连接入口。

静默辅助程序只处理已确认适配客户端路径的千牛进程，使用当前用户权限，不弹出注入窗口，不调用 `RunAs`，不提权。辅助程序与目标必须属于同一用户、会话和完整性级别。如果千牛通过“以管理员身份运行”启动而 JuDesk 普通运行，连接会失败并提示恢复方式；不会通过弹出 UAC 来继续。请让两个程序均以普通权限运行。

参考工程原有 `QNQtHelp64.exe` 要求管理员权限且带有进程管理行为，因此不直接复用。Windows 包使用 `JuDeskQianniuHook.exe` 加载参考工程的 `QnQtMsg64.dll`，代码与构建方式随仓库保留。macOS/Linux 不展示千牛入口，也不启动这些本地监听或携带 Windows Hook 文件。

## 运行结构

- Electron 主进程管理 HTTP/WS 页面桥接和 TCP `127.0.0.1:9996` Hook 连接。全部监听在回环地址，启动失败会显示端口错误，不会自动改用其他端口。
- 千牛 9.52 的本地聊天资源使用固定来源 `https://alires-webui`，页面桥接按这个精确来源放行；不放行同名子域、相似域名、HTTP 或其他端口。
- 页面桥接带本次运行令牌；TCP 按 `getusername` 返回的身份与页面登录身份配对，不使用全局“当前账号”。
- 登录身份兼容字符串和千牛 9.52 的 IM 用户对象：页面读取 `loginID.nick`，Hook 读取 `username.nick`，均保留完整子账号后缀，不使用数字 `targetId` 替代昵称。更新此脚本后须重启 JuDesk 并重新打开千牛聊天工作台，已加载的旧脚本不会随配置重连更新。
- 按完整客服登录名登记账号，按主账号昵称登记店铺；子账号 `店铺:客服` 归到主昵称对应店铺。暂不根据后来出现的 SDK 字段更换店铺身份。
- 页面暂存未获 ACK 的消息并在重连后重放，主进程等待业务服务入库成功才 ACK。去重由平台消息 ID 和现有业务层完成；缓存有上限，不承诺千牛关闭期间的离线消息补齐。
- Hook 回复没有可靠请求 ID，同一连接的命令串行执行。超时后断开该连接，防止迟到结果被误配给下一条发送。
- 发送命令成功不等于买家已收到。只有匹配到真实平台发送回显才能确认，否则使用既有的“待确认”发送状态，不伪造消息 ID，不自动重发未知结果。
- 自动 Hook 与 AI 自动回复是独立开关。接入不会跳过已有的收发验收、人工接管、接待策略和店铺权限。
- 同路径的多个千牛进程逐个尝试，某个进程失败不会阻止其他工作台进程。加载结果未确认（辅助程序退出码 11）按每个进程最多自动重试三次，间隔 15 秒；权限、架构等明确错误不反复重试，已经完成的身份握手不会被后续候选错误覆盖。

## 聊天侧栏与店铺客服 Toolkit

千牛接入共用的会话、收件箱、人工接管、发送队列和聊天侧栏。`builtin/commerce@1.4.0` 根据当前接待账号的实时能力开放千牛工具；已有工具挂载按现有升级规则使用最新版本，原 1.3.0 清单仍保留用于历史配置校验。

| 功能 | 接入方式与范围 |
| --- | --- |
| 收发消息 | 买家实时消息、千牛人工回复、JuDesk 文本及图片发送；原生文本/图片发送通过 Hook，消息通过页面 SDK 同步。 |
| 图片接收 | 下载平台可信 HTTPS 图片到本机附件，限制 8 MiB，供会话展示和已有图片处理流程使用。 |
| 店铺商品 | 关键词搜索、分页、价格/库存、商品属性；详情来自重新核验的当前商品列表，不包含未提供的 SKU 明细。 |
| 买家资料 | 当前买家的信用、会员/粉丝等平台返回资料，以及咨询、购买、浏览关联商品。 |
| 订单与物流 | 当前买家近三个月接口返回的订单、订单详情、物流轨迹和平台已提供的收件信息；按返回列表本地分页。 |
| 客服转接 | 侧栏查询在线客服，选择并确认个人转接；同时接入客服组、客服状态和组转接。排除自身、离线和挂起的个人客服。 |
| 商品操作 | 发送平台商品卡片、邀请下单；提交前重新核验商品与平台可用操作。 |
| 聊天历史 | 查询 JuDesk 本机已同步消息，支持游标翻页和撤回处理；界面及 Toolkit 明确范围，不能补齐平台离线历史。 |

商品、订单、客户资料和客服等平台查询通过当前账号已连接页面调用 `application.invokeMTopChannelService`，不在 JuDesk 中维护另一份千牛登录凭据。买家使用会话观察到的 ID/昵称与联系人查询结果精确核对。订单、商品、客服和客服组采用共用证据引用；前端或 Agent 不能自行指定另一店铺、买家或未查询到的操作目标。

个人转接、组转接和邀请下单沿用业务操作的确认、最终授权检查、去重与审计流程。个人和组转接会接管会话，邀请下单保持原接待模式。切换接待账号或页面重连会使正在执行的旧查询/操作失效，需要重新查询。个人转接传已核验的数字买家账号 ID，不传联系人搜索中的加密 ID。

文本发送回显按真实平台消息 ID、账号、会话、买家、内容和时间匹配；图片还要求实际图片字节的 SHA-256 相同；商品卡片要求回显中有明确商品 ID。原生请求实际写入后才登记回显候选，未提交或平台明确拒绝的请求标记失败；已提交但连接中断、超时或无法唯一匹配时保留“待确认”，不自动重发。平台转码造成图片字节不同也会保留待确认。原生协议没有请求 ID，若在已提交但结果未知的窗口内人工发送完全相同内容，仍存在关联歧义，需要核对平台记录。MTop 的 `sendCard: true` 只能证明接口受理，不能伪造为消息送达回执。暂存发送图片会保留以供 Hook 读取。

文本和图片的 Hook 受理后，JuDesk 会短暂、有限次查询该会话的 `PeekNewMsg`，补收没有触发页面通知的发送回显。收到新消息/发送消息通知时也只调用这个查看接口。不能主动调用会消费原生消息队列的 `GetNewMsg`，否则可能在千牛界面读取之前取走消息，导致客户收到而千牛聊天气泡缺失。千牛自身的 `GetNewMsg` / `PeekNewMsg` 回调仅被旁路观察；JuDesk 主进程发来的旧式 `GetNewMsg` 请求也转换为 `PeekNewMsg`。观察结果进入相同的持久化 ACK / 重放队列，SDK 卡住时停止追加查询，迟到回显仍可更新状态。

千牛 9.52 的自己发送流程先通过 `im.singlemsg.onSendNewMsg` 通知页面读取本地待发消息，再通过 `im.singlemsg.onMsgSendUpdate` 的 `sendStatus` 和 `mcode` 更新正式发送结果。JuDesk 按账号、会话和 `mcode.clientId` 暂存已观察到的原始消息及成功状态通知，双方齐备后将正式消息 ID 和发送时间合并到原消息，再核对账号、会话、买家、正文和时间；两种通知先后到达均可处理，切换账号时清空暂存。只接收 `sendStatus: 0` 且带非零平台消息 ID 的成功通知。

原消息查询 `im.singlemsg.GetOriginalMsgByID` 仅作为补充：2026-09-30 实机日志证实，该接口会返回 `{ msgType, code: { messageId, clientId }, ... }` 格式，不能假设它与 `GetNewMsg` / `PeekNewMsg` 的 `{ templateId, mcode, cid, fromid, toid, ... }` 格式相同。只有完整可验证的查询记录进入正常解析；本地待发消息与成功通知的关联不依赖该查询。只拿到 `clientId` 的待发消息、失败状态或账号/会话/消息 ID 不匹配的通知都不能确认发送。

允许多次发送相同内容，每次发送须对应不同的正式消息 ID。前一条已确认后再次发送相同文字可以正常确认；已有回执的重放不能确认下一条消息。如果多条同文发送都尚未确认且时间窗口重叠，协议仍不足以确定归属，应核对平台记录。提示“请勿重复发送”是防止把待确认操作盲目重试，不是限制发送相同文字。

若千牛已发送而句达一直显示“发送待确认”，先核对 Windows「设置 → 时间和语言 → 日期和时间」的自动校时及“立即同步”。平台消息时间与电脑发送时间不一致会阻止回显匹配，严重偏差还会使实时消息被当作历史记录。不能通过放宽匹配窗口或接受历史同文消息来消除提示。已在千牛核实的旧消息可点击气泡下的“已在平台确认”，不需要重新发送；更新桥接代码后应重启 JuDesk 并重新打开千牛聊天工作台，使新脚本生效。

尚未开放无可靠协议依据的千牛 SKU 查询、视频素材、订单备注、发货、退款和远端聊天历史。商品详情、较早买家足迹等不完整资料会明确标记，避免 Agent 把部分数据当成完整结果。参考项目的组转接示例同时含成功回执和参数待核实说明，组转接也需要随指定客户端实机验收。

## 验证与发布验收

自动化覆盖平台的 Windows 限制、空下载地址、启动引导、页面 SDK 延迟就绪、回环传输、账号隔离、消息 ACK、命令超时、原生进程生命周期、真实响应格式、订单号精度、买家范围校验、发送回显和转接最终授权。另有真实数据库的工作台/Toolkit 测试，以及侧栏查询和转接操作的浏览器验证。界面测试可运行：

```sh
node scripts/qianniu-setup-smoke.mjs
node scripts/qianniu-workbench-smoke.mjs
```

2026-09-30 在 Windows 普通权限的千牛 `9.52.00N` 实机上检查了聊天资源来源、对象登录身份、原生 DLL 加载及同一账号的 WebSocket/TCP 握手。原先直接以 `LoadLibraryW` 为线程入口没有载入模块，独立 Win64 线程函数调用同一加载器后成功载入并完成原生账号握手。随后用正式构建重启千牛和 JuDesk，确认辅助程序自动加载组件、两路连接恢复、账号登记为在线。此次排查没有发送客户消息；单账号连接验证、静态检查和模拟协议测试不能代替以下发布前验证：

1. 用指定版本的预处理客户端从固定 URL 加载脚本，登录后无 UAC、无注入窗口并自动在线。
2. 两个客服账号同时登录时，收到消息和发送回复均归属正确账号与会话。
3. 买家消息、千牛原生人工回复、JuDesk 文本及图片发送均有真实平台记录；回显缺失时保留待确认。
4. 千牛退出、切换账号、JuDesk 重启及电脑睡眠恢复后重新连接；不重复回复缓存消息。
5. 普通权限、进程权限不匹配、端口被占用、DLL/客户端版本不兼容均有明确状态，不弹出提权窗口。
6. 从聊天侧栏和店铺客服工具查询商品、当前买家资料、订单及物流，核对平台显示、金额和长订单号；切换会话不复用上一买家的数据。
7. 转接到在线客服/客服组，以及商品卡片和邀请下单，核对千牛接收方及明确回执；重复点击、转接期间断线、目标下线均不得造成重复操作。

`QnQtMsg64.dll` 为参考工程提供的闭源二进制，仍需要与发布所选的千牛版本完成上述 Windows 实机收发和重连验收。
